# Review r2 — D-TEXT-FIRST-007 v2 and its code; the features warning by words (ADR-125)

Reviewer: Codex, read-only, 2026-11-21. Verdict: REJECT. Answered by D-TEXT-FIRST-007 v3 and the code as changed after it.

**The ordinary copy retry uses the right keys. The blocking defects are in what happens after the copy exists and in how the chat decides that a first image is still needed.** A lost copy response can lead the editor back to an obsolete copy document. A lock takeover can still lead to a document write from the old tab. A stale empty visuals list can produce a second payable recap for a poster that already has an image.

### Blocking findings

1. **P1 — `firstImage` can offer another paid image from a stale empty list.** On ordinary opening, `adopt` reads visuals before assigning `creation`, and `firstImage` is a post-flush watcher behind the busy guard. That synchronous assignment is safe. The actual race is **between server reads**: `/visuals` returns empty, an in-flight scene finishes, then `/jobs` returns it as succeeded. `adopt` follows only queued or running jobs and never refreshes visuals for that completed scene. A reopened poster without a local waiting recap now qualifies. A jobs-read failure also returns with job state unknown. Once added, the first-image recap remains actionable even if visuals later arrive. **Smallest fix:** reconcile a succeeded scene/refinement’s `result_ref` with the visuals list before declaring the poster empty, keep unknown job state ineligible, and retire an untapped *first-image* offer if a version appears. Preserve rejection recaps, which intentionally offer another image. [App.vue:1218](frontend/src/App.vue#L1218) · [App.vue:1260](frontend/src/App.vue#L1260) · [ChatView.vue:274](frontend/src/ChatView.vue#L274) · [ChatView.vue:615](frontend/src/ChatView.vue#L615)

2. **P1 — takeover during copy adoption can send a PUT from the tab that lost the chat.** The checks immediately before the two copy POSTs are effective. After the second POST, `adopt` awaits `/visuals`. Steal the lock there without changing the first tab’s URL: the origin check passes, the old tab installs the document and changes its address, and `edit` queues an autosave under the lost hold. The new-poster path also calls unguarded `createPoster()`, which can issue `/creations` after takeover during the input request. **Smallest fix:** separate the hold check from source-thread persistence. Pass the hold check through `adopt` and chat-initiated `createPoster`, check it after waits before mutations, and keep the existing strict `sending` check for `/scenes`. Calling the present storage-writing `owned` after switching posters would verify the wrong thread. [App.vue:1183](frontend/src/App.vue#L1183) · [App.vue:1219](frontend/src/App.vue#L1219) · [App.vue:1944](frontend/src/App.vue#L1944) · [App.vue:2013](frontend/src/App.vue#L2013)

3. **P1 — replay adopts the original copy response as the current document.** Lose the copy response, open that copy from « Mes affiches », edit it or generate its image, then retry the source card. The keys correctly return **one copy**, but the idempotent response contains the creation-time document and revision. `adopt` combines that old document with current visuals. `remake` then unconditionally reveals the layers and queues a PUT against the old revision. Revision checking should prevent a silent server overwrite, but the editor can display obsolete content and enter save conflict. **Smallest fix:** use the mutation response for its ID, open the current creation through the existing read path, and apply any pending visibility initialization only to the untouched, versionless copy. Flush it before reporting initialization complete. ### Other defects and simplifications

- **P2 — the automatic recap can cancel the owner’s copy choice.** On a versionless source, sending photos supersedes its initial recap. Reload with the `photo` card open, return to the source after a successful copy, or let a copy attempt fail. `firstImage` sees no open **recap**, calls `recap()`, and `supersede` marks the `photo` card done. The owner loses « Copier… », « Réessayer » via the same copy action, or « Ouvrir la copie ». Resending the photos creates fresh keys and can make a second copy. The same race occurs if the owner sends photos during the initial photos GET. Give the explicit photo action priority. Restore the first-image offer after cancellation without superseding a pending read or its recovery card. ### Eight browser cases worth running

1. **Copy and charge end to end.** Send words and two originals on a versioned poster. Assert zero `/reads`, one new input with the expected assets and `supersedes_id`, one copy with the stored source revision and card key, and zero credit change. Tap the copy recap, verify its persisted request and key, then assert one scene job, one debit, the new input, and an unchanged source.
2. **Lost copy response, then edits on both sides.** Drop the response after server commit. Edit the source headline and open and edit the copy from the list. Retry the original card. Assert identical POST keys and bodies, one input and copy, current copy revision, preserved copy edits, and no conflicting visibility PUT.
3. **Storage refusal at the boundaries.** Refuse storage before the input POST, before the copy POST, after copy success, and before `/scenes`. Assert actual request counts at each boundary, accurate French status, recovery of the same copy, and zero debit when scene storage fails.
4. **Takeover and Back during adoption.** Delay the copy visuals GET. In one run steal the lock, in another navigate Back. Release the GET and assert the old tab sends no visibility PUT or scene, the intended address survives, and the copy remains recoverable. Attempt an attachment while the copy is pending.
5. **A scene finishes between the visuals and jobs reads.** Return empty visuals followed by a succeeded scene with a real result ID. Also restore a spent recap with its exact request. Assert no fresh payable card or key, then verify a genuine rejection still produces exactly one « Version refusée… » recap.
6. **Versionless source with an actionable photo card.** Send photos while its first photo lookup is delayed, reload with the offer open, fail and retry the copy, then return to the source. Assert the same card remains usable in each state. Switch to a second versionless poster while the first lookup is pending and verify the second gets its own photos and exactly one recap.
7. **New-poster regression and legacy restoration.** Attach and swap product/inspiration, generate through the `new`-to-poster move, and assert one scene with the selected reference. Restore an existing thread containing an ignored product-role attachment and verify its actionable recap shows only the real input assets.
8. **ADR‑125 in both interfaces.** Check a features request and « assombris l’affiche » or « fond plus sombre » in chat and editor, including accessible descriptions, cancellation, and a restored chat card. Verify cancellation sends no refinement.
