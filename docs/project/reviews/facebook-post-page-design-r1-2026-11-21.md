# Design review r1 — A publish page: one Facebook post with several posters (v1)

Reviewer: Codex, read-only, 2026-11-21. Verdict: REJECT (five P1, five P2). Answered by v2 of the design, rewritten the same day; see r2.

1. **P1 · Restore can turn a possibly public post into « non publiée ».** A backup holds `uploading`. The worker later commits `posting`, sends `/feed`, and loses the answer. The kept database now says `posting` or `unknown`. The restore rule imports only settled outcomes, so startup sees the backup’s `uploading`, marks it `failed`, and unlocks every poster. Reconcile both copies before startup recovery. If either copy says the final call may have left, preserve `unknown` unless the kept copy has a definitive settlement. [D-FB-POST-003 §4 and 006](docs/project/designs/facebook-post-page.md#d-fb-post-006--what-is-said-and-what-is-restored-covers-r-fb-post-007)

2. **P1 · Skipping a restored post loses the block on its surviving posters.** A kept `unknown` post contains A and B. Only A existed at backup time. Skipping the whole post lets the owner publish A alone without resolving the first post. Even when both posters survive, a newer confirmation can be missing and violate the proposed foreign key. Keep item IDs and hashes as historical references, as migration 0018 does for single publications. Restore the whole record and let missing thumbnails fall back. [Proposed schema and restore rule](docs/project/designs/facebook-post-page.md#d-fb-post-001--what-is-stored-covers-r-fb-post-003-005-006) · [Migration 0018](backend/migrations/versions/0018_facebook.py)

3. **P1 · The latest attempt ID does not establish what the owner knew.** A tab reads an `unknown` attempt. Another tab confirms it is present. Its ID stays the same, the pending block clears, and the first tab’s `seen` check can pass for another send. Separately, a later failed attempt can hide an earlier success because candidates expose only the latest IDs and dates, regardless of state. Return the latest attempt **and its state** for each publishing path, plus the latest successful publication for the warning. Freeze those values when the sheet opens and require fresh confirmation if they change. The existing single-poster UI already distinguishes `seenOf` from `publishedOn`. [D-FB-POST-003](docs/project/designs/facebook-post-page.md#d-fb-post-003--publishing-a-post-covers-r-fb-post-002-to-005) · [Existing UI rules](frontend/src/facebook.ts)

4. **P1 · A lost 202 followed by reload can become a fresh publication.** `mutation()` keeps uncertain keys in an in-memory `Map`. If Facebook publishes, the 202 is lost, and the browser reloads, the draft survives but the key disappears. Loading fresh candidates also supplies fresh `seen` values, so “retry” can pass admission as a new post. Persist the exact submitted body and key before sending, as the existing chat read does. Replay that pair and check for an existing row before file preparation, so a missing file cannot prevent recovery of an already accepted request. [D-FB-POST-005](docs/project/designs/facebook-post-page.md#d-fb-post-005--the-page-covers-r-fb-post-001-002-004-006) · [Client retry handling](frontend/src/api.ts)

5. **P1 · The last send check omits the shop limit.** Admit three images with a limit of three. Lower the limit to two during uploads. The worker checks closing, shop activity and Page identity, then sends all three. Check the current limit before the first upload and in the same write transaction that checks the Page and moves the row to `posting`. Define that commit as the cutoff for changes, and keep the Graph call outside it. This also closes the specified gap between the final Page check and the `posting` write. [D-FB-POST-003 §3](docs/project/designs/facebook-post-page.md#d-fb-post-003--publishing-a-post-covers-r-fb-post-002-to-005) · [R-FB-POST-005](docs/project/requirements/facebook-post-page.md#r-fb-post-005--publish-one-post-never-twice-never-half)

6. **P2 · A committed admission can have no worker.** If the route awaits admission in a thread, cancellation can arrive after SQLite commits `uploading` and before the route registers the task. A failed progress write can likewise end the worker with the row still `uploading`. The shop-wide gate then blocks even unrelated posters until restart. Have one registered, shielded task own admission through settlement, with the route awaiting only its admission result. Specify how a failed write is retried and how a dead worker’s row is recovered without resending `/feed`. The existing single-poster code registers its task **before** admission. [D-FB-POST-003 §3](docs/project/designs/facebook-post-page.md#d-fb-post-003--publishing-a-post-covers-r-fb-post-002-to-005) · [Existing task lifecycle](backend/src/affiche/posters/facebook_publish.py)

7. **P2 · The draft disappears on failure, and pagination can remove valid selections.** A 202 clears the order and description before image two fails. R-FB-POST-004 promises the draft until publication or explicit clearing. On reload, a saved poster on candidate page two is also absent from page one without being ineligible. Keep the submitted draft until confirmed publication, clear only that draft version, and resolve saved IDs directly before removing any. [D-FB-POST-005](docs/project/designs/facebook-post-page.md#d-fb-post-005--the-page-covers-r-fb-post-001-002-004-006) · [R-FB-POST-004](docs/project/requirements/facebook-post-page.md#r-fb-post-004--the-posts-description)

8. **P2 · A thumbnail loading does not verify the file the owner is publishing.** `/api/thumbnails/{sha}` returns a resized JPEG and permits caching. The sheet can enable « Publier » after that JPEG loads even if the confirmed PNG is now unreadable. Use thumbnails in the grid and load the shop-scoped confirmation download in the sheet. The existing download path checks the PNG hash and satisfies the exact-file requirement without a new endpoint. [D-FB-POST-005](docs/project/designs/facebook-post-page.md#d-fb-post-005--the-page-covers-r-fb-post-001-002-004-006) · [Thumbnail route](backend/src/affiche/api.py) · [Confirmed download](backend/src/affiche/posters/exports.py)

9. **P2 · The shutdown bound excludes cleanup and an upload retry.** Shutdown during image 30 can wait for the upload, its retry, then 29 sequential deletions at 20 seconds each. The stated “one call’s timeout plus settling” does not hold. On closing, skip retries and best-effort deletion, settle the pre-feed row, and leave the unpublished photos under the same rule as restart. The proofs established absence from the Page’s photo list. Visitor access by direct link and removal through Meta Business Suite remain unverified. [D-FB-POST-003 §4 and runbook](docs/project/designs/facebook-post-page.md#d-fb-post-003--publishing-a-post-covers-r-fb-post-002-to-005) · [Recorded proofs](docs/project/requirements/facebook-post-page.md#what-the-proofs-showed-2026-11-21-the-owners-word-you-can-run-them-graph-api-explorer-in-his-browser-graph-api-v270-the-page-token-of-original-phone-mada-every-post-scheduled-and-not-published)

10. **P2 · Two required explanations are missing from the composer.** A connected shop with unaccepted conditions gets a publish action but no specified acceptance path on this page. A user pasting a description gets a count line but no advance explanation of forbidden characters. Reuse the existing conditions action, specify the suspended-shop guidance, and put the 2,000-code-point and character rules beside the field. [D-FB-POST-005](docs/project/designs/facebook-post-page.md#d-fb-post-005--the-page-covers-r-fb-post-001-002-004-006) · [R-FB-POST-001 and 004](docs/project/requirements/facebook-post-page.md)

Read-only review. The Graph observations above come from the recorded proofs. No files were changed or live checks run.

**REJECT**
