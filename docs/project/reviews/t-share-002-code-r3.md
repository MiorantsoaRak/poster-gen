### Findings by severity

1. **High — The poll can present a known superseded confirmation as ready.** Tab A has a clean saver at N and polls a reused, confirmed render sourced at N. Tab B saves a different price at N+1. A’s poll reads the poster and receives `{revision: N+1, confirmation: null}`. `remember(read)` reduces that evidence to `null`. The source-revision clause then compares N to A’s saver at N and succeeds. The displayed price matches the old PNG, but « Votre affiche est prête » now points to a file the server just identified as superseded. **Fix:** retain the observed poster revision even for a null confirmation. When the poll observes a revision ahead of the saver, suppress current presentation and use the chat’s changed-elsewhere flow when local edits permit. [App.vue:1039](frontend/src/App.vue#L1039) · [App.vue:1474](frontend/src/App.vue#L1474) · [share.ts:10](frontend/src/share.ts#L10)

2. **High — Retrying `/jobs` can silently discard an edit.** The retry flushes once, then starts a poster GET through `discardAndReload()`. The editor’s price input remains editable during that GET. Enter a price after the GET starts and release the response within the 750 ms debounce. `adopt()` disposes the saver, cancels its timer, and replaces the document with the GET result. The entered price disappears without a PUT. **Fix:** capture the saver and its revision after the initial flush. Immediately before adopting the response, verify that the same saver is still clean and at that revision. If it changed, preserve the document and retry the reads after saving. [App.vue:1205](frontend/src/App.vue#L1205) · [App.vue:1284](frontend/src/App.vue#L1284) · [App.vue:1175](frontend/src/App.vue#L1175) · [autosave.ts:53](frontend/src/autosave.ts#L53)

3. **High — A delayed confirmation can attach render A’s download to render B.** Opening a poster can show its latest successful unconfirmed preview A and then follow an active render job B. Submit A’s checklist while B is running. If B’s poll installs B before A’s confirmation POST returns, `confirmFinal()` unconditionally assigns A’s URL to `confirmedDownload`. When B is sourced at the saved revision, the panel now labels **B’s unconfirmed preview** « Votre affiche est prête » and downloads **A**. The two renders can be different formats at the same revision. **Fix:** capture the submitted poster and render IDs, and apply the returned URL only while that preview is still displayed. Keeping the URL on its associated preview object also makes the ownership explicit. [App.vue:1208](frontend/src/App.vue#L1208) · [App.vue:1217](frontend/src/App.vue#L1217) · [App.vue:1478](frontend/src/App.vue#L1478) · [App.vue:1635](frontend/src/App.vue#L1635)

4. **Medium — Replacing an open preview can briefly put the old pixels beside the new price.** « Vérifier l’aperçu final » leaves the earlier panel mounted while the new job runs. When the poll replaces the preview, Vue reuses the same `<img>` and changes its `src`. The browser can continue displaying the previous image while the new PNG loads. The live price becomes visible immediately. `previewLoaded` gates the confirmation button only. **Fix:** key the image by render ID and show « Prix affiché » only after that render’s image has loaded. ### Undo, failed saves, and chat

**The second clause does not reopen the undo hole.** A confirmation named at N stops qualifying once the saver advances to N+1. Undo saved at N+2 restores content, but the cached name still carries N, and its render’s source revision is at most N. A fresh read can legitimately name an older render at N+2 only when a confirmation was recorded there. The backend checks the effective format hash and PNG and refuses to reuse a confirmation recorded at an older revision. A delayed `openFinal` read overtaken by a local save also fails `same()` before installation. [share.ts:10](frontend/src/share.ts#L10) · [App.vue:1616](frontend/src/App.vue#L1616) · [exports.py:180](backend/src/affiche/posters/exports.py#L180)

**A failed save or conflict preserves an already-open confirmed download.** The retained request keeps the saver dirty. The panel switches to the earlier heading, hides the price, and keeps the immutable download link enabled. There is a distinction for **reopening**: after closing the panel, the chat button calls `flush()` before doing its read. A persistently failing save or unresolved conflict blocks that route back to the file. If access from the chat button during save failure is required, allow a read-only opening of the known confirmation in the earlier-version presentation. Keep the flush before requesting a new render. With a clean saver, the chat already checks the poster-read revision before choosing the named GET or render POST.
