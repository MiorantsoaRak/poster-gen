Requested by the owner after using the deployed app. Audit only: no product implementation, commit, deployment or paid generation. Price stays drawn in the composition. The owner clarified that top-left / top-right placement means the **boutique's uploaded logo**, not the product brand.

## Additional findings

### 1. The app overpromises direct editing — high

The live introduction says “Vous pourrez ensuite ajuster chaque élément.” The library says posters can be reopened to change their price. With the preferred integrated composition, the title, price and product are not independent elements. The accurate explanation lives further down Textes, under “Pour la prochaine version”.

Replace the introduction with a short explanation that users prepare the text and style, then generate a version. Put a persistent “Ces changements seront utilisés pour la prochaine version” explanation beside fields that affect the raster, before editing, not only after a stale-image warning. Keep the price in the image, as requested. Maintain a clear distinction between the current image and the next generation's settings.

### 2. Existing posters can strand users without shop details — medium

The live QuietComfort Boutique panel contains the message that unavailable details must be entered on Create and then used in a **new poster**. The controls use `brand_snapshot`, captured at creation (`App.vue:438`, `store.py:183`). If a logo/contact did not exist then, updating the shop later does not make it available to that poster.

An explicit “Ajouter les informations actuelles de ma boutique” flow would be clearer than restarting. This needs requirements for updating the snapshot and for a new scene if the layout or drawn signature changes; never silently rewrite historical approved versions. Merely starting inclusion off does not erase an existing profile snapshot, so the requested default change should preserve that behaviour.

### 3. Version identification is ambiguous — medium, accessibility and usability

The live two-version poster exposes two “Choisir cette version (approuvée)” buttons and two “Comparer” buttons. Local three-version tiles are likewise unnumbered, even though the preview displays “Version 1/2/3”. All generated thumbnails use the same generic alternative text.

Number the tiles and their actions consistently with the preview: “Version 2 — approuvée”, “Choisir la version 2”, “Comparer la version 2”. Optionally include time when several posters/versions share names. A person should not need to remember thumbnail order to distinguish versions by keyboard or assistive technology.

### 4. Error explanations are not consistently associated with fields — medium

A 68-character title produces the visible French 60-character-limit message. The title field has `aria-invalid` but no `aria-describedby` or `aria-errormessage` connecting that text; brand/subtitle follow the same markup pattern. Price already uses `aria-describedby`, so there is a local pattern to reuse. Inline status messages can announce when they appear, but the relationship is not retained when returning to the field.

Add field-specific descriptions and put the relevant 60-character limit/counter by drawn text fields. [W3C's form-notification guidance](https://www.w3.org/WAI/tutorials/forms/notifications/) recommends associating field errors with their controls. This is a DOM/keyboard finding; speech output with NVDA, VoiceOver or TalkBack was not tested.

The local title-error screenshot also contains a revision conflict caused by the audit's two contexts selecting different versions of the same fixture. That is an intentional cross-context fixture side effect, **not** evidence of a new single-user save bug. “Bose prix” did not trigger a brand validation error; the artifact named `brand-error.png` is not evidence of one.

### 5. The displayed price estimate obscures the cheaper-model benefit — medium

The live new-version dialog says **“Coût estimé : au plus 0,40 $US.”** The dialog was cancelled and verified closed. This is separate from the owner's reported USD 0.26 total for today's usage, and from the earlier benchmark's per-image measurements.

Show a model-appropriate expected cost or range separately from the conservative accounting reservation. Do not imply that the reservation is a billed amount or a provider-enforced maximum. Verify current provider billing before changing a numeric estimate; this audit does not recalculate charges or release the earlier uncertain reserve.

### 6. Several terms still assume editor knowledge — lower priority

“Variante confirmée”, “Scène”, “Couleur d’accent” and “Fidélité” are understandable to an experienced owner but require inference on a first visit. The live variant field defaults to “Conforme à la photo”, which does not teach what a variant is. Prefer contextual hints such as “Couleur / modèle exact”, “Image complète” and “Vérifier le produit et les textes”. Keep technical placement/effect controls in advanced settings; keep ordinary generation settings easy to reach.

## Accessibility checks that passed, and their limits

- No page-wide horizontal overflow in the 34 captured states, including 320 px.
- All checked visible controls in touch contexts met the project's 44 × 44 px target. Smaller desktop controls were noted but are not automatically WCAG 2.1 AA failures: 44 × 44 is a usability target, not that standard's general AA requirement.
- No settled text-contrast failures using the existing browser checker on captured screens. This checks normal text against backgrounds, with the existing conservative glass calculation. It excludes placeholder text, text inside generated images and disabled controls. It does not certify every screen/theme or every translucent pixel. [W3C contrast guidance](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html) sets 4.5:1 for ordinary text, 3:1 for qualifying large text.
- The tabs responded to ArrowRight. Focus remained inside the review dialog after 20 Tab presses at each mobile size; Escape closed the enlarged scene at all three widths. Dialogs expose names/roles, and the page behind becomes inert.
- A dark/reduced-motion state was checked; not an exhaustive animation audit. No JavaScript errors occurred in the local walkthrough.
- The obscured controls are a verified pointer/discoverability problem. Do not declare a formal keyboard-focused WCAG failure from the scroll measurements alone. Keyboard focus under sticky content warrants a dedicated follow-up against [WCAG 2.2 Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

## Recommendation and next scope

For a nontechnical user, the first-poster sequence has a useful foundation: labelled steps, French feedback, explicit generation confirmation and an image review. Revising a poster is harder: controls disappear behind the preview, the UI does not consistently separate current image from next-version settings, and some shop changes require restarting.

1. Make mobile controls reachable and fix the clipped selection/focus outlines. Keep one compact preview with a clear collapse control and accessible full-screen inspection.
2. Prevent duplicated brand text and make the product-colour mode truthful, with visible text/palette confirmation before a paid request.
3. Apply the owner's identity-off default and design the original boutique logo's two placements across feed, square and story. Preserve saved profiles and approved versions.
4. Number versions, associate field errors, and clarify regeneration/cost language and missing-identity recovery.

These are audit recommendations, not an approved implementation design. Carry them into matching requirements/design/tasks before product changes; show the owner the proposed mobile arrangement before a broad visual rebuild. No need to replace the visual theme.

Not checked: real Android keyboard, low-end-device blur performance, screen-reader speech, actual browser zoom, generated-image colour/brand accuracy with a paid call, the user's historical orange request payload, and a complete final-export round trip. Edge's tool exposed its accessibility tree but not native screenshots or resize controls; mobile visual evidence comes from Chromium running the identical frontend assets. A helper request to read Edge's display-session environment was rejected by automatic approval review; it was not retried or bypassed.
