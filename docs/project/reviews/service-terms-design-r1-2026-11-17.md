**REJECT Draft v1.** The server has a suitable place to enforce acceptance for shop-paid operations. The release blockers are in erasure, the warning before payment, and the conditions dialog. As written, erasing one shop can remove another shop’s image, erasing the pilot can prevent the API from starting, and an owner can still pay for an unlisted-feature request without seeing the warning required by ADR-111.

### Critical

1. **D-TERMS-008, steps 2–4 — The ownership scan and file deletion race with uploads.** Shop B can upload the same bytes after the scan identifies a file as exclusive to A. Upload checks or writes the file **before** recording B’s access in SQLite. Erasure can then unlink the file and leave B with a valid reference to missing bytes. Moving the scan inside `write_tx` alone does not close that window. The backup copier can also finish copying a file after erasure. For this pilot, make `erase --yes` an offline maintenance operation. Hold the existing release/backup/restore lock, exclude the API, workers and other asset writers through the final unlink, and refuse to apply if exclusivity or the configured backup location cannot be established.
